# API для фронтенда

Единственный источник правды по API — Swagger. Этот файл только объясняет, как им
пользоваться; сами эндпоинты, поля и коды ошибок смотрите в UI, а не здесь — здесь они
успеют устареть.

| Что | Где |
|---|---|
| Swagger UI | `{BASE_URL}/api/docs` |
| Спека OpenAPI 3 | `{BASE_URL}/api/docs-json` |
| Спека в репозитории | `openapi.json` в корне |

Локально `BASE_URL` — `http://localhost:3000`, то есть UI живёт на
<http://localhost:3000/api/docs>.

Все роуты начинаются с `/api`: контроллер `auth` наружу доступен как `/api/auth/...`.

## Генерация клиента

`openapi.json` в корне репозитория обновляется командой `pnpm swagger:json` и коммитится.
Поднимать сервер, базу и RabbitMQ для этого не нужно. Файл лежит в гите намеренно:
изменение контракта видно в диффе пул-реквеста — там же, где о нём положено предупредить
фронтенд.

Забрать спеку можно тремя способами: из файла в репозитории, с живого стенда по
`/api/docs-json` или из артефакта сборки. Дальше — любой генератор, например:

```bash
# только типы
pnpm dlx openapi-typescript openapi.json -o src/shared/api/schema.d.ts

# типы + готовый клиент с хуками
pnpm dlx orval --input openapi.json --output src/shared/api/generated.ts
```

Имена методов в клиенте берутся из `operationId` и совпадают с именами хендлеров:
`login`, `logout`, `me`. Переименование хендлера на бэкенде переименует метод в клиенте,
поэтому это ломающее изменение — о нём предупреждаем заранее.

## Авторизация

1. `POST /api/auth/login` возвращает `accessToken` в теле и ставит httpOnly-cookie
   `refreshToken` на путь `/api/auth`.
2. Access-токен живёт 15 минут и уходит заголовком `Authorization: Bearer <accessToken>`.
3. Cookie из JS не читается — это защита от XSS. Чтобы браузер её принял и присылал,
   запросы должны идти с `credentials: "include"`.
4. `POST /api/auth/logout` гасит cookie. Токен не требует и всегда отвечает `200`: выйти
   нужно уметь и с протухшим access-токеном. Сам access-токен сервер не отзывает — он
   остаётся валидным до конца своего срока, стереть его у себя должен фронтенд.

```ts
const response = await fetch(`${BASE_URL}/api/auth/login`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include', // без этого cookie не сохранится
  body: JSON.stringify({ email, password }),
});
```

Домен фронтенда должен быть перечислен в переменной `CORS_ORIGINS` на сервере — иначе
браузер отсечёт ответ до того, как до него доберётся код. Нужен новый домен или стенд —
скажите бэкенду.

## Формат ответов

Правила действуют на всех эндпоинтах и для запроса, и для ответа:

- поля — `camelCase`;
- `id` и все ссылочные поля (`userId`, `postId`) — строка UUID, не число;
- даты — ISO 8601 в UTC: `2026-08-21T01:52:00.000Z`;
- пустая коллекция — `[]`, никогда не `null`. Для необязательных объектов и скаляров
  `null` допустим;
- успех — всегда `200`, в том числе на `POST`. `200` с ошибкой внутри тела не бывает.

## Ошибки

Тело ответа при любой ошибке одинаковое:

```json
{
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "Пользователь с таким email уже зарегистрирован",
  "details": [{ "field": "email", "message": "Email уже занят" }]
}
```

| Поле | Обязательное | Назначение |
|---|---|---|
| `code` | да | Стабильный машинный идентификатор, `UPPER_SNAKE_CASE` |
| `message` | да | Готовый текст для пользователя, на русском |
| `details` | нет | Уточнения по полям; у ошибок валидации — список ошибок формы |

**Ветвиться нужно по `code`, а не по тексту `message`.** Текст могут поправить в любой
момент как опечатку, `code` — часть контракта, и его переименование мы согласовываем
заранее. Коды, которые возвращает конкретный эндпоинт, перечислены в описании его
ответа в Swagger и лежат там же выпадающим списком примеров.

| Статус | Когда |
|---|---|
| `400` | Не прошла валидация или битые параметры. Код `VALIDATION_ERROR`, разбор по полям — в `details` |
| `401` | Нет авторизации или токен истёк |
| `403` | Авторизован, но прав на действие нет |
| `404` | Ресурс не найден |
| `500` | Непредвиденная ошибка. `message` всегда общий — подробности остаются в логе сервера |

Два кода на `401` различаются по смыслу: `TOKEN_EXPIRED` — access-токен протух, его нужно
молча обновить; `UNAUTHORIZED` — токена нет или он не годится, нужно показать форму входа.

Валидация включена в строгом режиме: лишнее поле в теле запроса не отбрасывается молча,
а даёт `400`. Отправлять можно только то, что описано в схеме запроса.

## Изменения контракта

Переименование поля, удаление, смена типа или `code` ошибки — ломающие изменения:
бэкенд предупреждает о них до мержа. Добавление необязательного поля ломающим не
считается и приезжает без предупреждения.
