Отревьюй пулл-реквест: `$1` (если аргумент пуст — PR текущей ветки).

## Собрать контекст

```
gh pr view $1 --json number,title,body,author,headRefName,baseRefName,files,additions,deletions
gh pr diff $1
gh pr checks $1
```

Если `gh pr view` не находит PR — сообщи об этом и остановись, не ревьюй вместо него локальный дифф молча.

Из ревью **исключить** сгенерированный код: `libs/prisma/src/generated/**`, `dist/**`, `pnpm-lock.yaml`.

## Что проверять

Первые семь пунктов — контракт с фронтендом из [CLAUDE.md](../../CLAUDE.md). Их нарушение ломает
не один экран, а сборку клиента, поэтому это всегда CRITICAL или HIGH.

### 1. Контракт ответов

- **Ключи JSON — `camelCase`.** Ни `snake_case`, ни `PascalCase`. Колонка в БД в snake_case маппится
  через `@map` в `prisma/schema.prisma`, наружу поле всё равно уходит camelCase.
- **`id` и все ссылочные поля (`userId`, `postId`, `authorId`) — строковый UUID.** Автоинкрементные
  числовые ключи наружу не отдаются. В схеме `@id @default(uuid()) @db.Uuid`.
- **Даты — ISO 8601 в UTC.** Не Unix-timestamp, не локальное время, не ручное форматирование на бэке.
- **Массив всегда массив.** Нет данных — `[]`, не `null`. Для необязательных объектов и скаляров
  `null` допустим.

### 2. Ошибки

- Доменные ошибки бросаются через `AppException` из `@app/common`, **не** через встроенные исключения
  Nest — у `NotFoundException` и родственников английские тексты (`Forbidden resource`), они уходят
  пользователю как есть.
- Новый `code` — `UPPER_SNAKE_CASE`, объявлен константой: общие в
  [libs/common/src/errors/error-code.ts](../../libs/common/src/errors/error-code.ts), доменные —
  рядом со своим модулем, как `AUTH_ERROR_CODE`. Строковый литерал прямо в `throw` — замечание.
- **Переименование или удаление существующего `code` — ломающее изменение.** Отметить отдельно:
  фронт ветвится по нему, требуется предупреждение до мержа.
- Ответы `5xx` обезличены. В `message` не утекают стектрейс, SQL, текст драйвера БД, имена таблиц.
- Статус по смыслу: `400` невалидный запрос, `401` нет авторизации или токен истёк, `403` прав нет,
  `404` не найдено, `500` непредвиденная. Не `200` с ошибкой в теле.

### 3. Валидация

Глобальный пайп включён с `whitelist` и `forbidNonWhitelisted` — лишнее поле в теле даёт `400`,
а не отбрасывается. Значит **каждый входной DTO обязан быть описан декораторами class-validator**;
поле без декоратора не пройдёт валидацию. Проверь, что новые DTO описаны полностью.

### 4. Swagger

Каждый новый или изменённый эндпоинт: DTO с `@ApiProperty`, ответы через `@ApiResponse`, ошибки —
через `@ApiErrorResponses(...)` (он подставляет общую схему `ApiErrorDto`). Эндпоинт без описания
в Swagger — HIGH: Swagger объявлен единственным источником правды по API.

### 5. HTTP-коды на POST

Nest на `POST` по умолчанию отвечает `201`. Если хендлер должен возвращать `200` — нужен
`@HttpCode(HttpStatus.OK)`. Отметь новые POST-хендлеры без явного кода.

### 6. Межсервисное взаимодействие

Монорепозиторий: `apps/gateway` (HTTP), `apps/auth`, `apps/notifications` (микросервисы через RabbitMQ),
общий код в `libs/common`, Prisma в `libs/prisma`.

- Вызовы микросервисов идут через `sendRpc` — в нём таймаут и разбор ошибки. Голый `client.send`
  без таймаута — замечание.
- Паттерны сообщений берутся из контрактов в `libs/common/src/contracts/`, не пишутся строкой по месту.
- В микросервисах ошибка уезжает через `RpcExceptionsFilter` / `toRpcErrorPayload`: всё, что не
  `AppException`, схлопывается в обезличенную 500. Проверь, что новый микросервисный хендлер не
  отдаёт наружу сырое исключение, а сам сервис регистрирует этот фильтр.
- Общий код, нужный больше чем одному приложению, живёт в `libs/common` и экспортируется из
  [libs/common/src/index.ts](../../libs/common/src/index.ts) — копия в двух `apps/` это дубль.

### 7. Инструментарий

- **Только pnpm.** `npm`, `yarn`, `bun`, `npx` в скриптах, CI, Dockerfile и документации — ошибка.
  Появление `package-lock.json` или `yarn.lock` — ошибка.
- Новый пакет с постинсталл-скриптом должен быть в `pnpm.onlyBuiltDependencies`.
- Миграции Prisma ходят по `DIRECT_URL`, приложение в рантайме — по `DATABASE_URL` (pooled).
  Перепутанные URL в конфиге — HIGH: миграции через pooler ломаются.

### 8. Безопасность

Отдельно пройди по diff, если он трогает авторизацию, пользовательский ввод, запросы к БД, файловую
систему или внешние API:

- Захардкоженные секреты, ключи, токены, пароли — CRITICAL всегда, включая тестовые файлы и `.env`,
  попавший в индекс.
- SQL-инъекции: конкатенация в `$queryRawUnsafe`, небезопасная сборка запроса.
- Обход авторизации: эндпоинт без guard там, где соседние с ним; проверка владельца ресурса,
  а не только факта аутентификации.
- Незалогиненный или, наоборот, слишком подробный лог: пароли, токены и тела запросов в логи не пишутся.
- Отсутствие rate limiting на эндпоинтах входа и регистрации.

### 9. Качество

- Функции < 50 строк, файлы < 800 строк, вложенность ≤ 4 уровней — иначе ранние возвраты.
- Ошибки обрабатываются явно, не глотаются молча.
- Нет `console.log` и отладочных остатков.
- Иммутабельность: новый объект вместо мутации существующего.
- Тесты на новую функциональность есть. Юнит рядом с кодом (`*.spec.ts`), e2e в
  `apps/gateway/test/`. Изменение формата ответа обязано отражаться в
  `apps/gateway/test/api-contract.e2e-spec.ts`.

### 10. Коммиты в PR

Проверь `git log` ветки: сообщения в формате `<type>: <описание>`, описание — от первого лица
в прошедшем времени (`добавил`, `починил`, `вынес`), не инфинитив и не повелительное наклонение.
Никаких упоминаний Claude, Anthropic, AI-ассистентов — ни в теле, ни в трейлерах.

## Формат отчёта

Сначала строкой: номер PR, заголовок, автор, ветка, объём диффа, статус CI из `gh pr checks`.

Дальше находки, сгруппированные по severity, самое серьёзное первым. Каждая находка:

- ссылка `путь/файл.ts:строка`
- в чём проблема — одним предложением
- конкретный сценарий поломки: какой ввод или состояние даёт какой неверный результат
- как чинить

| Severity | Когда | Действие |
|---|---|---|
| CRITICAL | Уязвимость, утечка секрета, риск потери данных, ломающее изменение контракта | Блокировать мерж |
| HIGH | Баг, нарушение контракта, отсутствие валидации или Swagger | Починить до мержа |
| MEDIUM | Поддерживаемость, дубли, отсутствие тестов | По возможности |
| LOW | Стиль, именование | На усмотрение |

В конце — вердикт: **Approve** (нет CRITICAL и HIGH), **Warning** (есть HIGH), **Block** (есть CRITICAL).

Не выдумывай находки ради объёма. Пустой список с явным «нарушений контракта не нашёл» — нормальный
результат. Каждую находку проверь по коду перед тем, как включать: убедись, что файл и строка
существуют и проблема реальна, а не выглядит правдоподобно.
